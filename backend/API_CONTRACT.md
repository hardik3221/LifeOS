# Proposed LifeOS API contract — v0.1

Status: implemented for local testing; not locked. Frontend and AI developer agreement is pending. Base URL: `http://localhost:8000`. JSON request bodies use `Content-Type: application/json`. `/openapi.json` describes concrete schemas; `/docs` is interactive.

## Endpoints

| Method | Path | Success |
| --- | --- | --- |
| GET | `/health` | 200 `{"status":"ok","database":"ok"}`; 503 on database error |
| GET | `/api/tasks` | 200 array of tasks |
| POST | `/api/tasks` | 201 task |
| GET | `/api/tasks/{task_id}` | 200 task |
| PATCH | `/api/tasks/{task_id}` | 200 updated task |
| DELETE | `/api/tasks/{task_id}` | 204, empty body |
| GET | `/api/goals` | 200 array of goals |
| POST | `/api/goals` | 201 goal |
| GET | `/api/goals/{goal_id}` | 200 goal (convenience endpoint) |
| PATCH | `/api/goals/{goal_id}` | 200 updated goal |
| DELETE | `/api/goals/{goal_id}` | 204, empty body |
| POST | `/api/planner/generate` | 200 schedule preview; 503 until AI adapter is connected |

List endpoints accept `offset=0`, `limit=100` (1–500), and optional `completed=true|false`. Responses are bare arrays, ordered by creation time then UUID. Omit `completed` to include all items. These are single-user endpoints; there is no authorization or ownership yet.

## Tasks

Create example:

```json
{
  "title": "Complete DSA practice",
  "description": "Solve array problems",
  "priority": "high",
  "deadline": "2026-10-12T18:00:00+05:30",
  "estimated_minutes": 60,
  "completed": false,
  "goal_id": null
}
```

Response example (IDs and timestamps generated by server):

```json
{
  "id": "6358c05d-5910-48d3-a675-f7ac1bcda72c",
  "title": "Complete DSA practice",
  "description": "Solve array problems",
  "priority": "high",
  "deadline": "2026-10-12T12:30:00Z",
  "estimated_minutes": 60,
  "completed": false,
  "goal_id": null,
  "created_at": "2026-10-11T08:00:00Z",
  "updated_at": "2026-10-11T08:00:00Z"
}
```

Only title is required. Title is trimmed and must have 1–200 characters. Description defaults to `""` and has at most 10,000 characters. Priority is `low|medium|high`, default `medium`. Estimated duration is an integer from 1 to 1440, default 30. Completed defaults to false. Deadline and goal ID default to null. A non-null goal ID must refer to an existing goal; otherwise 404. IDs are UUID strings.

PATCH accepts any subset of create fields; omitted fields stay unchanged. `{}` and unknown fields produce 422. Only `deadline` and `goal_id` may explicitly be null. Example completion update: `{"completed":true}`. `created_at` is immutable; writes update `updated_at`.

## Goals

Create accepts `title`, `description`, `deadline`, `completed`, with the same rules/defaults as tasks. Response adds `id`, `created_at`, `updated_at`. PATCH uses the same partial-update rules; only `deadline` may be null. Deleting a goal preserves its tasks and sets their `goal_id` to null.

## Dates

Send ISO 8601 timestamps with an explicit offset (`+05:30` for India, or `Z` for UTC). Task/goal deadlines without an offset are accepted for compatibility with the initial example and interpreted as UTC, **not browser-local time**. Responses normalize timestamps to UTC. No deadline is hardcoded or required. Planner window timestamps require explicit offsets; the frontend should use one consistent local offset for both boundaries and the matching local calendar date.

## Errors

Missing UUID resources: 404. Invalid UUIDs, bodies, bounds, empty updates and invalid fields: 422. Database errors: 503. Standard API HTTP errors use:

```json
{"error":{"code":404,"message":"Task not found"}}
```

Validation errors add a `details` array:

```json
{"error":{"code":422,"message":"Validation failed","details":[{"field":"body.title","message":"Field required","type":"missing"}]}}
```

Clients should branch on status/type rather than exact validation message text. CORS middleware can reject disallowed preflight origins separately with HTTP 400.

## Planner / Developer 3

Request:

```json
{
  "date": "2026-10-12",
  "available_start": "2026-10-12T09:00:00+05:30",
  "available_end": "2026-10-12T18:00:00+05:30"
}
```

Both boundaries must fall on `date` in their supplied offsets, with end after start. The backend passes `PlannerContext(tasks=[TaskRead, ...], goals=[GoalRead, ...])` containing unfinished records to the injected service. The service returns `PlannerResponse` (or a compatible dict):

```json
{
  "date": "2026-10-12",
  "schedule": [{
    "task_id": "6358c05d-5910-48d3-a675-f7ac1bcda72c",
    "start": "2026-10-12T09:00:00+05:30",
    "end": "2026-10-12T10:00:00+05:30"
  }],
  "unscheduled_task_ids": [],
  "notes": []
}
```

Every input task must appear exactly once, either in the schedule or `unscheduled_task_ids`. Schedule intervals must have positive duration, stay within the requested window, and not overlap; unknown task IDs and mismatched dates are rejected. The AI service decides priority and allocation, and may use estimated_minutes flexibly. The backend does not force estimated duration. No result is persisted. A missing service returns 503; provider failures and malformed output return 502 with a generic message. Changes needed for goal decomposition, stored schedules, rescheduling or an async engine must be agreed before extending this boundary.
